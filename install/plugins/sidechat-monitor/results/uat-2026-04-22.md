## Bugs surfaced

### Bug 1 — self-heal one-liner silently no-ops when `sc-version.txt` is empty

Present in both the **pre-2.6.6 skill** and the **2.6.6 skill**. On a fresh install
(or after any state reset that empties `sc-version.txt`), the guard
`[ -n "$L" ] && [ -n "$R" ] && [ "$L" != "$R" ]` short-circuits at `[ -n "$L" ]`,
so `sc-update.sh` never fires. Effect: the skill stays pinned at whatever version
was installed, and a server-side version bump doesn't propagate until sc-update.sh
is run manually.

**Concrete impact seen:** canary was on the pre-2.6.6 skill across the full quota-unlock window.
The first /mention-check fire (at 11:23) ran the **old skill** and used the Write
fallback (not MCP). Only after I forced `bash sc-update.sh` did the 2.6.6 skill
load; the second fire (at 11:29) used MCP correctly.

**Fix suggestion:**
```bash
L=$(cat "$SIDECHAT_DIR/sc-version.txt" 2>/dev/null)
R=$(curl -fsS --max-time 3 "$(grep ^SERVER_URL "$SIDECHAT_DIR/config" | cut -d= -f2)/install/version" 2>/dev/null | tr -d "\r\n")
[ -n "$R" ] && [ "$L" != "$R" ] && bash "$SIDECHAT_DIR/sc-update.sh" >/dev/null 2>&1 || true
```
i.e. drop the `[ -n "$L" ]` guard. Empty L compares as != to any non-empty R, which
triggers the update (desired behavior for fresh / reset state).

### Bug 2 — 2.6.6 self-heal one-liner drops `SIDECHAT_DIR` in subshell

In the 2.6.6 skill, the self-heal is written as:
```bash
SIDECHAT_DIR=/home/mcpcanary/.sidechat; bash -c 'L=$(cat "$SIDECHAT_DIR/sc-version.txt" 2>/dev/null); R=$(curl -fsS ...
```
`SIDECHAT_DIR` is **assigned** in the outer shell but not **exported**, so the inner
`bash -c '...'` doesn't inherit it. Inside the single-quoted heredoc, `$SIDECHAT_DIR`
expands to empty; `grep ^SERVER_URL "/config"` errors with
`grep: /config: No such file or directory`. The overall guard short-circuits
harmlessly, but the noise shows up in every auto-run.

**Fix suggestion** — use prefix form (exports for that one command):
```bash
SIDECHAT_DIR="$SIDECHAT_DIR" bash -c 'L=$(cat "$SIDECHAT_DIR/sc-version.txt"...
```
Or inline the whole check without the subshell.

Notably, Claude itself caught this during the run and flagged it in its end-of-turn summary:
> "the inline SIDECHAT_DIR export doesn't propagate into the bash -c subshell's parameter expansion, so $SIDECHAT_DIR was empty inside it."

## Adjacent observations (not plugin bugs)

- **Rate-limit modal persistence across quota-reset.** CC 2.1.117 stuck at the modal
  `"Claude Max → Stop and wait / Upgrade"` even after the quota reset at 12am ET.
  Required manual `Enter` in the tmux pane to dismiss before the REPL responded.
  Quota-aware auto-dismiss would be nice-to-have but out of scope.
- **Permission prompts fire even with broad allowlist** on some commands — Write
  `.sidechat/message.txt`, `rm` on `.sidechat/` paths, and notably the inline
  `for` loop resolver triggered CC's "expansion obfuscation" safety flag. With
  "don't ask again" selected for the common cases, subsequent runs should be
  quieter.
- **Stale-queue surfacing.** Two fenbot test mentions from 2026-04-22 01:10 and
  01:30 had been sitting in `new-mentions.txt` for ~10h because the prior Claude
  session was locked out behind the rate-limit modal. When I dismissed the modal,
  the plugin delivered them alongside jason's 11:15 test. Not a plugin bug —
  correct behavior (server holds unread mentions until client acknowledges) —
  but worth calling out: the plugin path doesn't "age out" old mentions like the
  `/messages/pending-mentions?since_hours=N` default suggests.
